# 跨端歌单双向增量合并与多端同步一致性修复计划 (v1.2.0)

## 1. 痛点与根本原因分析 (Root Causes)
- **用户反馈**：“我在手机上把一个歌添加进了歌单然后同步了，但是电脑上同步完成后没有看到那个歌。”
- **深度排查与根因**：
  1. **多端本地自增 ID 漂移与服务端重复建单**：
     - PC 端与 Android 端的本地 SQLite 数据库独立维护自增主键 `local_playlists.id`（例如 PC 上“日语”歌单 ID 为 `1`，手机上“日语”歌单 ID 为 `2`）。
     - 路由器服务端原本以 `id` 作为主键，导致同一名称的歌单在服务端被记录为两张独立歌单（`id: 1` 与 `id: 2`）。
     - 客户端下拉时收到两张同名歌单，顺序应用时出现后一个覆盖前一个，且在服务端未进行聚合。
  2. **客户端虚假时间戳导致覆盖（Stale Overwrite）**：
     - 原 `cloud.rs` 在向服务端推送歌单时，无论本地歌单是否被修改，均统一赋予 `updated_at = now`。
     - 本地 SQLite 未记录歌单的真实修改时间戳。导致未做修改的设备一旦发起同步，其过时的旧歌曲列表由于携带“最新时间戳”，直接强行覆盖了云端已被手机端更新的内容。
  3. **歌曲列表全量覆写而非并集增量合并**：
     - 当多端离线或分别添加歌曲时，服务端与客户端均采用全量数组覆盖逻辑，缺乏基于歌曲唯一标识 `track.key` 的集合合并（Union Merge），导致多端添加的歌曲互相冲刷覆盖。
  4. **服务端日志处理缺陷**：
     - `server.py` 在处理异常日志时参数解构可能引发 `IndexError`，导致偶发性中断。

## 2. 解决方案与执行计划
- [ ] **步骤一：服务端数据去重、合流与双向集合合并 (`sync-server/server.py`)**
  - 重写服务端歌单索引与合并机制：改以歌单名称 `name`（去除首尾空白）为跨端权威唯一识别键，禁止服务端产生同名重复歌单。
  - 实现基于 `track.key` 的全量歌曲并集增量合并算法（Track Union Merge）：无论哪一端添加了新歌曲，合并结果均完整保留并去重，杜绝歌曲丢失。
  - 服务端启动与同步时自动清理现存重复歌单历史，将重复同名歌单的歌曲自动合并入单一条目。
  - 修复 `log_message` 的格式化调用以增强系统稳定性。
  - 更新部署至路由器并重启 `nons-sync` 系统服务。
- [ ] **步骤二：客户端本地数据库与修改时间戳真实追踪 (`storage.rs` & `store.rs`)**
  - 在 SQLite `local_playlists` 表中增加 `updated_at INTEGER NOT NULL DEFAULT 0` 字段及自动迁移。
  - 在歌单创建、添加歌曲（`Write::Add`）、移除歌曲（`Write::Remove`）、重命名（`Write::Rename`）、重排序（`Write::Reorder`）等修改时，原子更新 `updated_at = now_seconds()`。
  - 导出歌单信息与向云端上报时，真实传递各自歌单的 `updated_at`，不再盲目伪造 `now`。
- [ ] **步骤三：客户端智能拉取与无损应用 (`cloud.rs` & `store.rs`)**
  - `apply_cloud_playlist` 逻辑升级：在拉取云端歌单合并本地时，对本地可能存在但云端未同步的歌曲做安全保留合并，并同步更新本地 `updated_at`。
- [ ] **步骤四：双端验证与测试**
  - 启动路由器服务并验证 API 歌单去重与合并。
  - 测试 PC 端与 Android 端双向添加歌曲、同步后歌曲一致性。
- [ ] **步骤五：重新编译打包并交付产物**
  - 编译 Windows 桌面端 Release 安装包。
  - 编译 Android ARM64 APK 安装包。
  - 归档至 `release-packages/` 并更新结果文档。
